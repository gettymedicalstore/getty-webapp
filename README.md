# Getty Medical Store

Next.js 16.2, React 19, Tailwind 4 and TanStack Query. Read the installed Next.js guides in `node_modules/next/dist/docs/` before changing framework APIs.

## Run locally

```sh
npm install
cp .env.example .env.local
npm run dev
```

The public API configuration is `NEXT_PUBLIC_GETTY_API_BASE_URL=https://api.gettymedicalstores.com`. Restart development after changing it; rebuild for production because Next.js includes public environment values in the browser bundle. A missing value uses this live origin. There is no mock mode or local backend.

## Form validation

All forms use React Hook Form with a Zod resolver. Use `ValidatedForm` and the `FormInputField`, `FormInput`, `FormSelect`, and `FormTextarea` controls in `components/shared/form/validated-form.tsx` for new forms. The shared form always sets `noValidate`, disables native validation, and displays accessible field errors. Schemas in `lib/form-schemas.ts` normalize text and numbers before submission; authentication and contact forms also reuse their feature schemas.

Controlled OTP, country/phone, file uploads, and variant options use RHF controllers or field arrays. Automatic filters validate before applying, without a submit button. Registration drafts accept incomplete fields while validating supplied values. Keep API validation in place as a separate boundary.

## Live API integration

Browser data requests go directly to the live Getty API. Public server rendering fetches the same public catalog. The old `app/api` proxy routes, seeded accounts, locally signed sessions, mock catalog, device cart and in-memory order/payment repositories have been removed.

Connected operations include:

- Login, token renewal and logout at `/auth/getty/login`, `/auth/getty/refresh` and `/auth/getty/logout`.
- Signed-in password changes use `PATCH /getty/v1/tenant/password/change` with only `{ currentPassword, newPassword }`. The dialog opens directly with current, new and confirm password fields. Confirmation is validated locally with React Hook Form and Zod; no email code or verification reference is required.
- Public password recovery requests, OTP verification and password updates at `/getty/account/v1/password/reset/{username}`, `/getty/account/v1/password/reset/verify` and `/getty/account/v1/password/reset/confirm`.
- Public categories, product lists/details, variants, published reviews and photos under `/getty/ecommerce/catalog`.
- Customer signup, email confirmation and resend under `/getty/ecommerce/onboarding/v1`.
- Authenticated cart reads and variant quantity updates/removals under `/getty/v1/order/cart`.
- Inventory balances/history, adjustments and thresholds under `/getty/v1/inventory`.
- Product/category administration, tax management, customer/vendor details, team-profile lists and tenant account creation through their documented Getty paths. Customer and vendor detail pages use `/getty/v1/tenant/tenants/{id}` and group returned information into Overview, Contact & address, Business details and Account information tabs.
- Product image upload preparation, signed storage uploads and product photo attachment.
- Admin dashboard at `GET /getty/v1/dashboard`: account/catalogue counts, monthly order trend, orders needing attention and products awaiting approval. Zero counts and empty attention lists are valid results; malformed responses show a retry state.

API calls use shared Axios instances with a 15-second timeout. Authenticated requests carry Getty’s server-managed cookies and the current access token when available. Public catalog reads send neither bearer tokens nor cookies, even when a user is signed in. Login and signup omit the bearer header and never trigger renewal. The user profile and credentials persist in local storage across navigation, reloads and tabs, with an in-memory fallback when storage is blocked. Passwords are never stored. Cross-tab sign-out clears the visible session and query cache. Delayed responses cannot overwrite or erase a newer login. The app does not create authentication cookies or sign its own tokens. UI role routing is only a navigation aid; the Getty backend enforces access.

The Axios response interceptor handles both HTTP `401` responses and Getty envelopes with `status: 401`. It calls `/auth/getty/refresh` and retries each original request at most once. Concurrent failures share one renewal; Web Locks coordinate browser tabs where supported. Authentication endpoints bypass renewal. JSON token responses replace the saved credentials. Successful cookie-only refresh responses preserve the user profile, drop the expired bearer header and use cookies for subsequent requests. A persisted credential version coordinates cookie-only rotation across tabs. A refresh `401`/`403` preserves the account, records a rejected-renewal flag and shows a sign-in prompt rather than automatically logging out. New sign-in or successful rotation clears that flag. Network outages, malformed responses and cancellation do not erase the account. Cancelling one request does not cancel renewal needed by other requests.

Buyer-cart reads and mutations are restricted to consumer accounts. Store headers/product cards do not request a buyer cart for admin/vendor sessions. Staff/vendor visits to the cart show a customer-account prompt, and checkout routes them back to their workspace. This avoids irrelevant buyer authorization failures immediately after login. `/login?reauthenticate=1` opens the login form even while an account is saved; reauthentication never needs to clear the account first.

Refresh follows the user-supplied cookie-based Axios example: `POST /auth/getty/refresh` with JSON `{}`, `withCredentials: true`, and no expired bearer or JavaScript refresh-token body. Refresh/logout use a separate Axios instance so they cannot recursively refresh themselves. Refresh accepts a successful JSON token envelope or a successful cookie-only response, including an empty 200/204 body. Existing users need to sign in once after this change so the browser can receive the API cookies that the previous `credentials: "omit"` transport ignored. Cookie names and attributes belong to the Getty backend; this frontend does not guess or read HttpOnly cookies. Successful renewal with a live account remains unverified; automated tests use synthetic fixtures through the real Axios interceptors.

The live service must allow the exact frontend origin and credentialed CORS requests. On 2026-10-06, read-only login and refresh preflights returned `Access-Control-Allow-Origin: http://localhost:3000`, `Access-Control-Allow-Credentials: true`, and allowed `content-type, authorization`. This verifies preflight configuration, not actual browser cookie storage or live token renewal. Browser cookie policy and backend cookie attributes still apply. Authenticated mutations are covered with fixtures, not live account changes. Empty catalog results remain empty states rather than sample stock.

The updated OpenAPI export now documents authenticated password changes. Live refresh verification still needs confirmation. See the endpoint audit below. Orders, checkout/payment, account editing, analytics, contact delivery and newsletter endpoints also remain undocumented. These operations show an unavailable state and do not call invented URLs or fall back to local repositories. Old payment-return URLs do not claim a payment succeeded or clear the cart.

### Password recovery

The forgot-password flow posts the encoded email in the reset-request path, then verifies a six-digit code using `{reference, otp}`. These requests send neither credentials nor bearer tokens, do not attempt token renewal, and preserve any existing signed-in session. Initiation uses the supplied response's `data.reference` and `data.expiresAt`. Resend becomes available at that absolute expiry; a missing, null or blank `expiresAt` starts a five-minute resend countdown after the response. The deadline is saved for reloads and is replaced after a successful resend. Initial code expiry is enforced at the verification step when the service supplies `expiresAt`; the fallback only controls resending. Initiation also accepts a direct reference. Verification requires a valid returned reference and six-digit OTP, either directly or in Getty's `data` envelope. Missing or invalid verification details display a service error and cannot advance the flow.

The final step calls `PATCH /getty/account/v1/password/reset/confirm` with `{reference, otp, password}` using the endpoint supplied on October 7, 2026. Both reference and OTP come from the OTP verification response, with leading zeros preserved. A new reset request clears both verified fields, and verification responses from an older request cannot advance the flow. The backend validates these returned credentials independently of the initial email code's expiry. Password confirmation stays in the form, and the success screen appears only after the backend accepts the update. No separate endpoint environment variable is required. The OTP remains in memory; reloading the password page requires verification again. Recovery tests use synthetic responses without sending live reset emails or changing passwords.

### Product image uploads

The Photos tab offers single-image and multiple-image upload dialogs. Selecting valid images immediately initiates each upload with metadata through `POST /getty/v1/attachments/files`; its response identifies the file in `data.file` and supplies the storage `url`, `method` and `headers`. Each preview shows its preparation status and can retry failed preparation. Image bytes are sent only when the user clicks Upload, which stays disabled until the complete selection is ready. The client uses the prepared signed URLs and headers, with no Getty bearer token or cookies. After every image uploads successfully, `POST /getty/v1/product/products/photos` attaches their file IDs with `{product, files}`. Failed uploads remain retryable, completed files are reused, and the user can prepare unfinished images again if an upload URL expires. Closing the dialog or removing an image discards late preparation results. Contract tests cover preparation without storage writes, confirmation without re-initiation, signed query parameters and partial upload retries without writing to live storage. Routing multiple-image initiation through `/getty/v1/attachments/batches` still requires that endpoint's request and response contract.

The managed-product adapter retains the returned `links.self`, `links.attachments` and `links.photos`. For published products, the Photos tab reads the supplied public photo link and displays saved images after reload. It parses `data.records`, retaining each photo's ID, name and MIME type, and resolves the returned relative `url` against the Getty API origin. Source links must match the requested product and file; returned query parameters are preserved. Photo pages forward both `nextCursor.entry` and `nextCursor.id`; `nextCursor: null` ends pagination. The returned page limit is retained. Upload completion refreshes the gallery and file IDs keep local previews from duplicating backend records. Loading and failed requests remain distinct from an empty gallery. Draft image uploads still work, but listing their saved files through `links.attachments` requires that endpoint's response contract.

## Navigation

The admin menu includes Vendors and Customers. Both pages use the same tenant table, search, pagination and account details dialog. The list calls `GET /getty/v1/tenant/tenants` with `type=vendor` for Vendors and `type=customer` for Customers; each page enforces its own type filter and keeps its query cache separate.

Authentication pages in `app/(auth)` share a focused layout outside the marketing layout. Login, signup and verification preserve the shopper’s destination with validated return paths. Cart and checkout in `app/(purchase)` have a compact header and progress indicator. Skeletons cover route transitions and asynchronous data. Device-only wishlist, address preferences and notification settings remain explicitly local conveniences; they are not backend records.

Signing in from the store header opens the account's dashboard: Getty support admins go to `/admin`, vendor accounts to `/supplier`, and consumer accounts to `/customer`. Tenant type is checked alongside profile role so an administrator of a vendor or consumer organisation stays in that organisation's workspace. Protected return links stay within the correct workspace; customers can also resume their shopping or checkout destination. Signed-in visits to the login page redirect automatically. Store navigation shows the account's name, organisation, role, dashboard and order links on desktop and mobile, with sign-out available in the account menu.

The login response may omit an ID; the email then identifies the session. Organisation, account status, organisation status and password-reset flag are preserved from the response. Getty's encrypted access tokens are sent unchanged, without trying to decode them as ordinary JWTs. A null media field uses the initials avatar.

Workspace menus share one definition for desktop and mobile. Admins have Dashboard, Vendors, Product (Categories, Taxes, Products, Inventory), and Orders. Consumers have Orders and Account; `/customer` opens Orders. Vendors have Orders, Product (Taxes, Products, Inventory), and Account. `/supplier` opens `/supplier/orders`. Customer and vendor Orders pages serve as their landing dashboards with order/payment summary cards, quick actions and order history. Summary metrics describe loaded orders and remain unavailable when order data cannot be fetched; customer/vendor order endpoints still need their backend contract. Product groups expand and collapse, and nested routes retain their active section. Account pages link to preferences and the relevant delivery or business details. `/admin/suppliers` redirects to Vendors at `/admin/vendors`; vendor workspace URLs remain under `/supplier`. Tax list/create/edit/delete operations are connected for both admin and vendor workspaces.
